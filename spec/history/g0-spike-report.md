## S1: Verify with CI=true

**Ran.** `spikes/s1`: net11 TUnit 1.76.45 exe with `Verify.TUnit` 33.3.4, `Directory.Build.props` with `Deterministic=true` and `ContinuousIntegrationBuild=true` under `CI=true`; text and `.cs` snapshots, then a real `CSharpGeneratorDriver` result through `Verify.SourceGenerators` 2.5.0 and through a local helper. `dotnet test --project`, on Windows and in `dynasharp-ci:rc3`.

**Result.**
- `.verified.cs` and `.verified.txt` are found and compared, on Windows and Linux. `DeterministicSourcePaths=false` is not needed in the csproj because `Verify.props` (buildTransitive) sets `Deterministic=false` and `DeterministicSourcePaths=false` itself; the package value wins over the repo's `Directory.Build.props` `Deterministic=true`, so the test project compiles non-deterministically. Forcing `DeterministicSourcePaths=true` in the csproj breaks it: Verify reports `Directory: /_/spikes/s1` and never finds the files. Do not set it.
- Verify takes the test file's directory from the compiler-recorded source path, which `DeterministicSourcePaths=true` rewrites to `/_/...`; that is why the forced setting breaks the lookup.
- `Verify.SourceGenerators` 2.5.0 loads under Verify 33.3.4 (it ships no net10 or net11 asset; no downgrade warning, no runtime error). `Verify(driver)` produced one `Name#A.g.verified.cs` per generated tree and a `.txt` with diagnostics when there are any (checked with a generator reporting an error).
- The local helper also works, with a real driver result:

```csharp
var result = CSharpGeneratorDriver.Create(generator).RunGenerators(compilation).GetRunResult();
var targets = result.GeneratedTrees.Select(t => new Target("cs", t.GetText().ToString(), Path.GetFileName(t.FilePath)));
return Verify(new { Diagnostics = result.Diagnostics.Select(d => d.ToString()) }, targets);   // using VerifyTests; static VerifyTUnit.Verifier
```

  It produced `...#A.g.cs.verified.cs`. Passing `Path.GetFileNameWithoutExtension` as the name would give `#A.g.verified.cs` like the package; that tweak is not run.
- Three confirmations of section 9: `*.verified.cs` is globbed into `Compile` (CS0101 duplicate type when two exist) so `<Compile Remove="**/*.verified.cs;**/*.received.cs" />` is required; Verify throws `VerifiedLineEndingException` on a CRLF verified file, so the LF rule in `.gitattributes` is mandatory (Verify's own message suggests `*.verified.cs text eol=lf working-tree-encoding=UTF-8`; the repo's `* text=auto eol=crlf` would otherwise win); received files are written next to the sources.

**Not in the design: Verify 33 has a sponsorship gate.** `Verify.targets` runs a SponsorCheck task; without a property the build fails with `SC021`. Options it prints: a GitHub sponsor account, a time-bounded licence, a publisher-defined exemption (`OpenSource`, `SmallRevenue`, each needs `Verify_SponsorshipExemptionUntil`, at most 12 months out, so it is a yearly renewal), or `Verify_SponsorshipLicenseIgnored=true` which builds with an `SC023` warning and states the build is in breach of the licence. I did not choose any for the project. With `Verify_SponsorshipExemption=OpenSource` plus `Until=2027-10` in a throwaway props file the build is clean. This is the owner's call and a legal claim, not mine. If the owner does not want to declare one, the dependency is the problem, and a local snapshot comparer (read `.verified.cs`, compare, write `.received.cs` on mismatch, fail with a diff; about 40 lines, LF-only) removes Verify and the fee. Recommendation if Verify stays: `Verify.TUnit` plus the local helper, not `Verify.SourceGenerators` (last release 2024-09, built on Verify 26.5, adds nothing the helper lacks).

**Apply to the test csproj if Verify stays:**

```xml
<PackageReference Include="Verify.TUnit" />                      <!-- 33.3.4 in Directory.Packages.props -->
<PropertyGroup>
  <Verify_SponsorshipExemption>...</Verify_SponsorshipExemption> <!-- owner decision -->
  <Verify_SponsorshipExemptionUntil>yyyy-MM</Verify_SponsorshipExemptionUntil>
  <!-- Verify scans the project dir, its parent and grandparent for solutions. tests/DynaSharp.UnitTests sees two slnx
       at the root and warns (an MSBuild warning, not promoted by TreatWarningsAsErrors; set explicitly anyway). -->
  <SolutionDir>$(MSBuildThisFileDirectory)../../</SolutionDir>
  <SolutionName>DynaSharp</SolutionName>

<ItemGroup><Compile Remove="**/*.verified.cs;**/*.received.cs" /></ItemGroup>
```

Also: `*.verified.* text eol=lf` in `.gitattributes`, `*.received.*` in `.gitignore` (both already in the design).

If a generator class (a `[Generator]` type) is ever declared in the test project itself, `Microsoft.CodeAnalysis.Analyzers` (flows from `Microsoft.CodeAnalysis.CSharp`) reports RS1036 and RS1041 there. Not an issue while the generator lives in its own project.

**Design changes.**
1. **Defect in section 4.** The positional-record tail `return new global::Shop.Address(fields.Street, fields.City, fields.Zip);` fails with **CS8604** (possible null argument) because `__Fields fields = default;` leaves reference fields maybe-null for flow analysis. The `[SetsRequiredMembers]` path is not affected, because there `fields` is an `in` parameter and its fields count as declared. Fix: emit the null-forgiving operator on every constructor argument whose type is a non-nullable reference or unconstrained generic type, after the `__set` checks: `new global::Shop.Address(fields.Street!, fields.City!, fields.Zip)`. The operator on a value type is accepted without a warning, so it can be emitted unconditionally for non-nullable arguments.
2. **`Keys.Of` and the key struct** (replaces `EntityKey<T>`). Compiled and ran as: `Order.Keys.Of(userId, createdAt, orderId)` returns a nested `Keys.PrimaryKey : IKey<Order>`, a `readonly struct` holding the placeholder values (no string) and implementing `void WriteKey(DynamoDbWriter writer)` by calling `Pk.Write` and `Sk.Write`. Interfaces: `IKey { void WriteKey(DynamoDbWriter writer); }` and `IKey<TEntity> : IKey where TEntity : IDynamoDbEntity<TEntity>`. With `Table<T>.Get<TKey>(TKey key) where TKey : IKey<T>`, `TKey` is inferred and a key of another entity is a compile error, which plain `IKey` would not give. Nesting the struct in `Keys` keeps `Keys` the only reserved name (DYNA014).
3. **DYNA015** must emit nothing for that type. At C# 10 the generated file alone produces dozens of unrelated errors (CS8936, CS8706, CS8703), which hide the one DYNA015.
4. **`KeyWriter` signature rule for G3.** Every span parameter that the writer only reads must be `scoped`. Without it `KeyWriter` itself fails at `WriteLiteral(text[..prefix])` (a stackalloc buffer), CS8350 and CS8352. With `scoped`, all generated call sites are accepted as is.
5. **Sparse indexes** were written as the amendment says (all attributes of the index, or none): `if (entity.TrackingId is { } __k0 && entity.ShippedAt is { } __k1) { ... }`. Pattern variables declared in a condition with `&&` leak into the enclosing scope, so the indexed names (`__k0`, `__k1`) must be unique per method, as the design already says.
6. Section 5.4 compiles as written in `DynamoDbReader` (`ReadAttribute<T, TConverter>` using `ref this`, `GetAttributeNameUtf8`, `GetStringUtf8`, `Unescape`), but StyleCop SA1202 requires the private `ValueUtf8` and `Unescape` after the public and other private members, and SA1507 allows no double blank line.
7. User-facing: generated code needs no `using` and no implicit usings (verified with implicit usings off). `Keys` and nested key classes with public members had XML docs in this run; see S4 for what happens without.

**Design changes (section 1 and 9).**
1. **Lock files.** Adding a `PackageVersion` for `Microsoft.CodeAnalysis.CSharp` to `Directory.Packages.props` makes BenchmarkDotNet's transitive copy `CentralTransitive`: `benchmarks/.../packages.lock.json` changes (still resolves 5.6.0, requested `[5.0.0, )`) and locked restore fails with NU1004 until regenerated. `DynaSharp` and `AotSmoke` lock files do **not** change from the `ReferenceOutputAssembly="false"` reference. A test project that references `Microsoft.CodeAnalysis.CSharp` directly gets 26 new lines (Direct 5.0.0, Common, Analyzers). So "all project lock files get regenerated" is too broad: new generator lock file, Benchmarks, UnitTests.
2. **Locked mode does not require a lock file.** With `CI=true` and the generator's `packages.lock.json` deleted, restore succeeds and silently re-creates it. A forgotten lock file for a new project is not caught by locked mode. Add a CI step that fails on `git status --porcelain` after restore (or checks the file list).
3. **Pack must not be RID-specific.** With `-r linux-x64` the generator builds into `bin/Release/netstandard2.0/linux-x64/`. The Linux AOT publish is unaffected (it does not pack). `dotnet pack -r` on a clean tree fails loudly with NU5019, but on a tree with a stale non-RID output it silently packs the stale dll. The generator lock file contains RID targets for the four RIDs (inherited `RuntimeIdentifiers`), so RID restore works. Keep the `PackageSmoke` content check the design already has, and build the package from a clean checkout without `-r`.
4. The generator assembly reports version 1.0.0.0 (MinVer does not apply to it). Harmless, but give it the same version if it ever appears in diagnostics or support output.

## S4: IsExternalInit, external-file diagnostics, CS1591

**Ran.** `spikes/s4`: `Gen` (netstandard2.0, LangVersion 12, Roslyn 5.0.0) with an internal `IsExternalInit` polyfill, public records and init types, and an optional `InternalsVisibleTo` to `Consumer`; a generator; `Consumer` (net11, `GenerateDocumentationFile`, references `Gen` as assembly and analyzer). All under `CI=true`.

**IsExternalInit.** With IVT on (`Consumer` used `S4Gen.Hidden`, an internal type, proving IVT was active), a consumer that declares a record, an `init` accessor and uses `with` builds with **no CS1685 and no CS0433**. A conflict exists only when the consumer's source names the type: `typeof(System.Runtime.CompilerServices.IsExternalInit)` gives CS0433 (exists in both `S4Gen` and `System.Runtime`). Public generator types with `init` and records are usable from the consumer in both configurations. So the design's reason for making test-facing types public does not hold: `InternalsVisibleTo` from the generator to `DynaSharp.UnitTests` is safe, and `KeyTemplateParser`, `EquatableArray<T>` and the model can stay `internal`. Making them public is still harmless; this is a choice, not a constraint. CA1812 for the generator class is a separate matter.

**External-file diagnostics in `dotnet build`.** `Location.Create(path, textSpan, lineSpan)` built from data captured in the transform prints, under `CI=true`:

```
D:\...\Consumer\Bad.cs(4,14): error DYNA900: Class 'Bad' is bad
D:\...\Consumer\Model.cs(5,14): warning DYNA901: Class 'Warn' is suspicious
```

File, line and column are correct (path mapping from `ContinuousIntegrationBuild` does not rewrite them). `/warnaserror` promotes the warning as usual. But suppression is limited, matching the design's expectation and going further:

| Mechanism | External-file location | Real tree location |
|---|---|---|
| `#pragma warning disable` around the type | **does not suppress** | suppresses |
| `.editorconfig` `dotnet_diagnostic.X.severity = none` or `error` | **has no effect** | works |
| `.globalconfig` (`is_global = true`) | works | works |
| `<NoWarn>` | works | works |

The design says `#pragma` fails and `NoWarn` works, which is right, but it does not say `.editorconfig` also fails, and `.editorconfig` is where most users tune severity. Of the section 7 diagnostics, DYNA108 and DYNA110 are warnings that users will want to tune.

**Change.** Keep the transform and the model free of `Location`, and build the real location in a separate output node that is the only node touching the compilation, so the cached generation nodes are unaffected:

```csharp
var withLocations = diagnostics.Where(static d => d.Diagnostics.Count > 0).Combine(context.CompilationProvider);
context.RegisterSourceOutput(withLocations, static (spc, pair) =>
{
    foreach (var tree in pair.Right.SyntaxTrees)
    {
        if (tree.FilePath == pair.Left.FilePath) { /* Location.Create(tree, span) for each DiagnosticInfo */ break; }
    }
});
```

This ran: with the tree-based location, pragma and `.editorconfig` both work (DYNA903 in the spike). The node reruns on every compilation change, but it does a path scan only for types that have diagnostics. Keep the `FilePath, Span` fields in `DiagnosticInfo`; drop `LinePositionSpan`, which `Location.Create(tree, span)` computes itself. I did not verify IDE rendering; the build output is the evidence. If the owner prefers the design as written, then document that only `NoWarn` and `.globalconfig` silence DYNA108/110, not `#pragma` and not `.editorconfig`.

**CS1591 in `<auto-generated/>`.** It fires. A generated file with the `// <auto-generated/>` header and a public type and member without XML docs gives `warning CS1591` for both, printed with the virtual path `obj/Debug/net11.0/S4Gen/S4Gen.SpikeGenerator/NoDocs.g.cs(3,21)`. A `#pragma warning disable CS1591` at the top of the generated file silences it. Analyzer rules (CA, StyleCop) do not report in these files: the S2 files with public nested classes and `latest-all` produced none. So: either document every public generated member (as section 4 does) or emit `#pragma warning disable CS1591`; the pragma is cheaper and cannot be forgotten per member. Note that `tests/.editorconfig` sets `CS1591` to `none` for `tests/`, which also covers generated trees in `obj` under the test project, but a consumer's `src` project gets the warning.

## S5: analyzer diagnostic beside CS4007

**Ran.** `spikes/s4`: a `DiagnosticAnalyzer` `DYNA201` in the generator assembly and a consumer with a `ref struct Cmd` in four cases: local across an await, command in the awaited expression then reused, capture in a lambda, field of the type.

**Result.** The compiler positions are: CS4007 on the identifier use after the await (`Async.cs(22,13)` for `_ = cmd.Set(1);`, `(32,15)` for the reused `cmd` in `await cmd.Set(2).SendAsync()`), CS8175 on the captured identifier, CS8345 on the field type.

| Case | Compiler error | Can DYNA201 sit beside it? |
|---|---|---|
| Local across await, command reused after await | CS4007 | **Yes, if the analyzer finds it itself.** `compilation.GetDiagnostics()` in a compilation action does not contain CS4007 (lowering error); a syntax and symbol rule does: an identifier bound to a ref struct local, used after an `await` that follows the local's declaration, in the same method. Reported on the identifier, it has the identical span. |
| Capture in lambda | CS8175 | Yes, even through `GetDiagnostics()` filtering by id (a method body binding error), identical span |
| Field of command type | CS8345 | **No.** A declaration-phase error stops csc before analyzers run: neither the `GetDiagnostics()` approach nor a field analyzer produced any output |

`dotnet build` prints both lines, the compiler error first, with the same file, line and column, and counts both:

```
D:\...\Async.cs(22,13): error CS4007: Instance of type 'M.Cmd' cannot be preserved across 'await' or 'yield' boundary.
D:\...\Async.cs(22,13): error DYNA201: A command is built and sent in one expression. Compute values first, or move the chain into a method. (https://example.invalid/dyna201)
```

The help link from `helpLinkUri` is appended to the message text in the console. With the rule at warning severity it prints as `warning DYNA201` next to the error (`Build FAILED. 3 Warning(s), 1 Error(s)`, two of the warnings were unrelated CS1591).

**Design changes (api-design 3.4, generator design section 7).**
1. Do not implement DYNA201 as "report next to CS4007 by reading the compiler's diagnostics": that works for binding errors (CS8175, CS4012, CS4013 by the same mechanism, not run for the last two) and not for CS4007. Implement it as a syntax and symbol rule that mirrors the compiler's rule, restricted to ref structs declared by DynaSharp (a name check on the type's containing namespace), and cover CS8345 by documentation only.
2. Make DYNA201 a **warning**, not an error: the rule duplicates compiler logic, and a false positive on code that compiles must not break a build. When the compiler error exists the build fails anyway.
3. The rule needs the `CompilationEnd` custom tag (RS1037) only if it uses a compilation action, which the recommended approach does not.
4. An analyzer needs `EnableConcurrentExecution` and `ConfigureGeneratedCodeAnalysis(None)`; with `EnforceExtendedAnalyzerRules` RS2008 demands the release-tracking files once any descriptor exists.
5. The analyzer shipping in the generator assembly was run as such (same dll, `OutputItemType="Analyzer"`), so no second assembly is needed.
