## 1. Public API

One new public type, `DynaSharp.Testing.FakeDynamoDb`, plus two public enum-free helpers on it. Everything else internal under `src/DynaSharp.Testing/Fake/` (namespace `DynaSharp.Testing.Fake`, as `Fluent` holds internals in `DynaSharp.Fluent`). Name: `FakeDynamoDb`, because `requirements.md` and `tasks.md` call it "the fake" and the package already uses role names (`Stub*`, `Recording*`); "InMemory" describes the implementation, not the role.

```csharp
namespace DynaSharp.Testing;

/// An in-memory DynamoDB that speaks the wire protocol behind an HttpMessageHandler, for functional tests: state a test sets up and reads back.
public sealed class FakeDynamoDb
{
    public FakeDynamoDb(TimeProvider? timeProvider = null);     // TimeProvider.System by default. Drives CreationDateTime, TTL sweeps, transaction idempotency windows.

    // Clients and handlers
    public StubHandler CreateHandler();                          // new StubHandler(Answer). Enqueue on it injects faults; Requests records; the fake is shared by every handler of this instance.
    public DynamoDbClient CreateClient(Func<DynamoDbClientOptions, DynamoDbClientOptions>? configure = null);         // StubClient.Create(CreateHandler(), configure)
    public DynamoDbStreamsClient CreateStreamsClient(Func<DynamoDbClientOptions, DynamoDbClientOptions>? configure = null); // P6 only

    // The wire, for a responder or a server
    public StubResponse Answer(RecordedRequest request);         // operation from X-Amz-Target, body as sent
    public StubResponse Answer(string operation, string requestJson);  // "GetItem", "DynamoDBStreams_20120810.GetRecords" or "GetRecords"; what RawDynamoDb and the HTTP tool call

    // Tables (synchronous, no client needed; the yats fixtures)
    public TableDescription CreateTable(CreateTableRequest request);     // same code path as the wire; throws ResourceInUseException / ValidationException (DynaSharp's own types)
    public TableDescription CreateTable<T>(string tableName) where T : IDynamoDbEntity<T>;  // what Table<T>.CreateTable() would send, built by the same internal (TableSchema / TableAdministration); same constraint as StubResponse.Table<T>
    public TableDescription DescribeTable(string tableName);     // throws ResourceNotFoundException
    public void DeleteTable(string tableName);
    public IReadOnlyList<string> TableNames { get; }
    public void Reset();                                          // drops every table, item and idempotency token; the handlers stay valid

    // Items (synchronous; the same storage path as PutItem/GetItem/DeleteItem without conditions: key validation, size limit, index maintenance)
    public void Put(string tableName, Item item);
    public void Put<T>(string tableName, T entity) where T : IDynamoDbDocument<T>;   // written as PutItem writes the entity (keys, discriminator, version), through WriteAttributes as StubResponse does
    public Item? Get(string tableName, Item key);
    public T? Get<T>(string tableName, Item key) where T : IDynamoDbDocument<T>;    // read through the entity's own code
    public bool Delete(string tableName, Item key);
    public IReadOnlyList<Item> Items(string tableName);           // snapshot in key order (partition by key bytes, then sort key by DynamoDB's rules)
    public IReadOnlyList<T> Items<T>(string tableName) where T : IDynamoDbDocument<T>;
    public int ExpireItems();                                      // deletes every item of a table with TTL ENABLED whose TTL attribute is a number <= now on the clock; returns the count. TTL never fires by itself.
}
```

Rules:
- **Getting a client**: `StubClient.Create(fake.CreateHandler())` works unchanged, `fake.CreateClient()` is the short form. `CreateHandler()` returns a real `StubHandler` whose responder is `Answer`, so the whole existing vocabulary applies: `handler.Requests` (`RecordedRequest`, recording reused as asked), `handler.Enqueue(StubResponse.DynamoDbError("ProvisionedThroughputExceededException", ...))` for the next request (the fake does not see it, so state does not change, as with a real throttle), `ThrowIfResponsesLeft`. Conditional and "lost response" faults: `new StubHandler(r => { var answer = fake.Answer(r); return r.Operation == "PutItem" ? StubResponse.DynamoDbError("InternalServerError", ..., HttpStatusCode.InternalServerError) : answer; })` (state changed, response lost: the pattern of `Recipes/LostResponseClient.cs`). No fault API of its own on the fake: `StubHandler` is it. Document the two patterns in the Testing README.
- **Tables**: never implicit. A request on an unknown table answers `ResourceNotFoundException` ("Cannot do operations on a non-existent table") like DynamoDB. Three ways to create: over the wire (`CreateTableRequest`, `Table<T>.CreateTable()`), `fake.CreateTable(request)`, `fake.CreateTable<T>(name)`. Tables and indexes are `ACTIVE` in the response of `CreateTable`/`UpdateTable` already (opinion; `WaitUntilActiveAsync` returns at once; Dynoxide answers CREATING then ACTIVE, DynamoDB Local ACTIVE, both pass the tests today). `DeleteTable` frees the name at once (same as both emulators, `Gap.TableGoneAtOnce` already describes this).
- **Direct item API** bypasses expressions and conditions only; it validates keys against the schema, the 400 KB limit and the key size limits, and it maintains indexes. Errors are the DynaSharp exception types (`ValidationException`, `ResourceNotFoundException`), built from the same internal `FakeError` the wire renders, so a fixture fails the same way a client would.
- **Time**: `TimeProvider` as above. TTL is stored and reported (`DescribeTimeToLive`), reads do not hide expired items (DynamoDB does not guarantee that either), `ExpireItems()` is the background sweeper under test control. `ClientRequestToken` of `TransactWriteItems` is remembered for 10 minutes on the clock.
- **Thread safety**: one `Lock` in the fake; every `Answer` and every direct call runs under it, start to end, synchronously (nothing awaits inside). Several clients and handlers over one fake are fine; a `BatchWriteItem` is atomic as a whole here, which is stricter than DynamoDB and not observable by a test that passes on DynamoDB.
- **Isolation**: one `FakeDynamoDb` per test (`new`, no static state, nothing to dispose). The integration suite shares one per run and keeps apart by table name, like the emulators.
- **Observability**: none of the fake's own (it is a test double); the client's spans and metrics are exercised as with any handler.
- **PublicAPI.Unshipped.txt**, the Testing README (new section "A fake DynamoDB"), `spec/api.md` section 16 (new rows), `spec/architecture.md` (module map row and a new section 14 "The fake"), `docs/testing.md` (user-facing scope lists) all change in the same commits as the surface.

## 2. Scope

### Operations in
GetItem, PutItem, UpdateItem, DeleteItem, Query, Scan (including `Segment`/`TotalSegments`), BatchGetItem, BatchWriteItem, TransactGetItems, TransactWriteItems, CreateTable, DescribeTable, DeleteTable, UpdateTable (billing mode and throughput, GSI create/update/delete, stream specification in P6), ListTables (`Limit`, `ExclusiveStartTableName`, `LastEvaluatedTableName`), DescribeTimeToLive, UpdateTimeToLive, DescribeLimits (fixed account numbers; Dynoxide has a gap for it, the fake need not). Streams (ListStreams, DescribeStream, GetShardIterator, GetRecords) only with P6; until then `StreamEnabled: true` is rejected with the unsupported error below, never accepted silently.

### Semantics in (what a functional test can rely on)
- Keys: schema validation (`The provided key element does not match the schema`), key types S/N/B, empty string or empty binary key rejected, partition key <= 2048 bytes, sort key <= 1024 bytes, item size <= 400 KB (name bytes + value bytes with DynamoDB's documented size rules, one `ItemSize` class used for the limit, the 1 MB page and capacity units), number validation (<= 38 significant digits, exponent range 10^-130 to 10^126, no NaN/infinity, canonical form stored as sent).
- Ordering: sort keys by DynamoDB's rules, S by UTF-8 bytes unsigned, B by bytes unsigned, N numerically with arbitrary precision. Partition order of a Scan is deterministic (ordinal of the partition key bytes); tests must not depend on it, as on DynamoDB.
- Condition expressions: full grammar (`=`, `<>`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `IN` up to 100, `AND`, `OR`, `NOT`, parentheses, `attribute_exists`, `attribute_not_exists`, `attribute_type`, `begins_with`, `contains` (string in string, element in set, element in list), `size` of S/B/L/M/SS/NS/BS), document paths with nested maps and list indexes, DynamoDB's type rules (a comparison of different types is false, not an error; `size` of a scalar number or bool is a `ValidationException`), ExpressionAttributeNames/Values resolution, reserved words rejected when bare, unused names or values rejected (`Value provided in ExpressionAttributeNames unused in expressions: keys: {#a}`), a placeholder that the maps lack rejected.
- Update expressions: SET (with one `+`/`-`, `if_not_exists`, `list_append`), REMOVE (attributes and list elements), ADD (number, and sets of the same type), DELETE (sets), each section once, overlapping paths rejected (`Two document paths overlap with each other`), a path through a missing parent rejected (`The document path provided in the update expression is invalid for update`), list index past the end appends, ADD on a non-number rejected, an update that creates the item (upsert) writes the key attributes, DELETE that empties a set removes the attribute, 38-digit arithmetic.
- Key conditions: partition `=`, sort `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `begins_with` (on S and B), nothing else (anything else is a `ValidationException` as on DynamoDB); `ScanIndexForward`.
- Filters applied after `Limit` and after the page cut (so a filtered page can be empty and still carry `LastEvaluatedKey`); `Count` and `ScannedCount`; `Select` (ALL, ALL_PROJECTED, SPECIFIC, COUNT) with DynamoDB's rules (SPECIFIC without projection is an error, COUNT with projection is an error, ALL_ATTRIBUTES on a KEYS_ONLY/INCLUDE GSI is an error).
- Projection expressions with nested paths and list indexes; keys are not added unless projected (the `TransactGetProjectionWithoutKeys` behavior of real DynamoDB, which Dynoxide lacks).
- Pagination: `Limit` counts items read before the filter; the 1 MB page by `ItemSize`; `LastEvaluatedKey` holds the table key plus the index key for an index read; `ExclusiveStartKey` validated against the schema (an empty one is an error, see the decision in `tasks.md`).
- Indexes: GSIs with `ALL`, `KEYS_ONLY`, `INCLUDE`; sparse (an item is in an index iff every index key attribute is present with the declared type); index key attribute of the wrong type on write is a `ValidationException`; `ConsistentRead: true` on a GSI is a `ValidationException`; LSIs with consistent reads and the sort key of the table in `LastEvaluatedKey`; GSI backfill is instant.
- Writes: `ReturnValues` all five with DynamoDB's rules (PutItem and DeleteItem take only NONE/ALL_OLD), `ReturnValuesOnConditionCheckFailure: ALL_OLD` puts `Item` into the `ConditionalCheckFailedException` body, condition failure message `The conditional request failed`, `ReturnConsumedCapacity` TOTAL and INDEXES with the documented arithmetic (reads: ceil(size/4 KB) units, half for eventually consistent, GSI reads carry their own share; writes: ceil(size/1 KB) with the larger of old and new image, plus index units per changed index key as documented; transactions twice; batch per table), `ReturnItemCollectionMetrics: SIZE` for tables with an LSI (`SizeEstimateRangeGB: [0, 1]`).
- Batches: up to 100 keys / 25 writes per request, 16 MB not enforced; duplicates in a `BatchWriteItem` rejected; `UnprocessedItems` and `UnprocessedKeys` are always empty (never produced; fault injection covers that path, as today with stubs).
- Transactions: all-or-nothing under the lock, up to 100 actions, the same item twice rejected (`Transaction request cannot include multiple operations on one item`), `CancellationReasons` with one entry per action (`Code: None` for the others, `ConditionalCheckFailed` with `Item` when asked), `ClientRequestToken` idempotency: same token and same request within 10 minutes replays the result, different request is `IdempotentParameterMismatchException`. `TransactionConflict`, `TransactionInProgress` never (there is nothing concurrent; `Gaps.cs` already documents them as unproducible everywhere).
- TTL: `UpdateTimeToLive` enable/disable at once (`ENABLED`/`DISABLED`, not `ENABLING`), enabling twice is a `ValidationException` as on real DynamoDB (Dynoxide has a gap for it, the fake should not).
- Errors: HTTP 400 for every client error, `__type` with the `com.amazonaws.dynamodb.v20120810#` prefix, exact code; `x-amzn-RequestId` on every answer (a new GUID); the client maps everything through `ErrorMapper` as with any backend.

### Out (what a test cannot rely on)
Eventual consistency (every read sees the last write), throttling and capacity enforcement (`ProvisionedThroughputExceededException` never happens by itself, provisioned numbers are stored and reported only), index backfill timing, `TransactionConflict`, `UnprocessedItems`/`UnprocessedKeys`, exact `SizeEstimateRangeGB`, the 10 GB item-collection limit, the 16 MB batch response limit, PartiQL (`ExecuteStatement`, `BatchExecuteStatement`, `ExecuteTransaction`), backups, PITR, export/import, Kinesis destinations, tags, resource policies, Contributor Insights, global tables, DAX, vector search, `DescribeEndpoints`, legacy parameters (`AttributesToGet`, `KeyConditions`, `QueryFilter`, `ScanFilter`, `Expected`, `AttributeUpdates`, `ConditionalOperator`), the exact validation order and message text (code is exact, message is best effort following the Developer Guide / DynamoDB Local / Parity captures where quoted in this plan), `x-amz-crc32` as a validated checksum, automatic TTL deletion, multiple stream shards.

### How the fake reports what it does not do (fail loudly, never differ silently)
- Unknown `X-Amz-Target` (PartiQL, backups, tags, ...): HTTP 400, `__type: com.amazonaws.dynamodb.v20120810#UnknownOperationException`, message `FakeDynamoDb does not implement <Op>. It is not supported.` This is what DynamoDB Local sends for an unknown operation and what the Parity Suite's probe takes as a skip.
- A known operation with a member or a value the fake does not implement (a legacy parameter, `StreamSpecification` before P6, an unknown top-level member, an unknown enum value): HTTP 400, `__type: DynaSharp.Testing#UnsupportedByFakeException`, so `DynamoDbException.ErrorCode` is `UnsupportedByFakeException` and the message names the member, the operation and the scope section of `docs/testing.md`. Rule for every request reader: **every top-level member must be consumed by name; an unconsumed member is this error.** No request member is ever ignored.
- A `ValidationException` the fake raises for a request DynamoDB would accept is a bug of the fake, and the Parity run or the integration suite catches it; the Gaps row of the fake may only name what the "Out" list names (see 4).

## 3. Architecture

All under `src/DynaSharp.Testing/Fake/`, `internal` except `FakeDynamoDb`. The fake runs the client's path in reverse: it **reads** request JSON and **writes** response JSON, which the library never does (it writes requests, reads responses), so almost nothing of the client's operation code can be echoed. Not a hot path: `JsonDocument`/`JsonElement` for envelopes, LINQ allowed, correctness over allocation. AOT: no reflection, no `dynamic`, no `System.Text.Json` serialization of CLR types (only `JsonDocument` and `Utf8JsonWriter`). No new package.

### Components and files

**Wire layer** (`Fake/Wire/`)
- `FakeWire.cs`: `static FakeAnswer Handle(FakeDatabase db, string? target, ReadOnlySpan<byte> body)`. Strips the `DynamoDB_20120810.` / `DynamoDBStreams_20120810.` prefix, looks the operation up in a `Dictionary<string, OperationHandler>` (`internal delegate void OperationHandler(FakeDatabase db, JsonElement request, Utf8JsonWriter response)`), runs it under `db.Gate`, renders the answer; catches `FakeError` and renders the error body; anything else propagates (a bug of the fake must crash the test, not become a 500).
- `FakeAnswer.cs`: `readonly record struct FakeAnswer(HttpStatusCode StatusCode, byte[] Body, string RequestId)`; `ToStubResponse()`.
- `FakeError.cs`: `sealed class FakeError : Exception { string Code; HttpStatusCode Status; Action<Utf8JsonWriter>? ExtraBody; }` with factories `Validation(message)`, `ResourceNotFound()`, `ResourceInUse()`, `ConditionalCheckFailed(Item? returned)`, `TransactionCanceled(reasons)`, `IdempotentParameterMismatch()`, `UnknownOperation(op)`, `Unsupported(what, op)`. `ToDynamoDbException()` for the direct API (reuses `ErrorMapper.Map` on the rendered body, so the direct API throws exactly what a client would).
- `RequestJson.cs`: the request readers. `ReadItem(JsonElement)` (hands the element's raw UTF-8 to `AttributeValueConverter.ReadItem` through a `DynamoDbReader`), `ReadKey`, `ReadString`, `ReadInt`, `ReadBool`, `ReadEnum<T>(JsonElement, EnumWireNames<T>)` (reuses `WireNames` so the spelling of every enum has one source), `ReadStringMap`, `ReadAttributeValueMap`, `Members(JsonElement, params ReadOnlySpan<string> allowed)` which throws `FakeError.Unsupported` on any other member.
- `ResponseJson.cs`: `WriteItem(Utf8JsonWriter, Item)` through `DynamoDbWriter` + `AttributeValueConverter.WriteItem`, `WriteItems`, `WriteConsumedCapacity`, `WriteTableDescription(FakeTable)` (the one writer of table descriptions; `StubResponse.Tables` may be refactored onto it later, optional), `WriteCancellationReasons`.

**Expression engine** (`Fake/Expressions/`), its own code end to end
- `ExpressionTokenizer.cs`: text to tokens (`Word`, `NamePlaceholder`, `ValuePlaceholder`, `Number`, comparator, punctuation), with a position for messages. Independent of the generator's lexer (which cannot be referenced and works on compile-time parts with holes). The keyword and function lists are spelled again here; a unit test keeps them equal to `ExpressionWriter.ConditionKeywords`/`ConditionFunctions` as `ExpressionWriterTests` already does for the generator.
- `ExpressionParser.cs`: recursive descent to an AST: `ConditionNode` (`And`, `Or`, `Not`, `Compare(op, Operand, Operand)`, `Between`, `In`, `Function`), `Operand` (`Path`, `Value(AttributeValue)`, `Size(Path)`, `IfNotExists`, `ListAppend`, `Sum(+/-)`), `UpdateAction` (`Set(Path, Operand)`, `Remove(Path)`, `Add(Path, Value)`, `Delete(Path, Value)`), `DocumentPath` (segments: name or index). Grammar as `ExpressionParser` of the generator accepts it; the error strings follow DynamoDB's `Invalid ConditionExpression: Syntax error; token: "x", near: "..."` shape.
- `PlaceholderScope.cs`: resolves `#n`/`:v` from the maps, records what was used; `ThrowIfUnused()` is called once per request after every expression of that request was parsed (DynamoDB checks per request, not per expression).
- `AttributeComparer.cs`: `Compare(AttributeValue a, AttributeValue b)` for S, N, B with the ordering rules; `Equals` structurally (reuses `AttributeValue.Equals` except for N, which compares numerically through `DecimalNumber`); the type rules of conditions.
- `DecimalNumber.cs`: arbitrary precision number (`BigInteger` coefficient, `int` exponent), `Parse(string)` with DynamoDB's limits (`FakeError.Validation` otherwise), `Add`, `Subtract`, `CompareTo`, `ToString()` canonical as DynamoDB echoes (trailing zeros trimmed, exponent form only when needed). Not `DynamoDbNumber` (that parses to CLR types and would lose digits).
- `ConditionEvaluator.cs`: `bool Evaluate(ConditionNode, Item? item)`; functions and `contains`/`size` per type.
- `UpdateApplier.cs`: `Item Apply(IReadOnlyList<UpdateAction>, Item? current, Item key)`; path validation, overlap check, list semantics, set arithmetic, returns the new image; also computes `UPDATED_OLD`/`UPDATED_NEW` deltas.
- `KeyConditionCompiler.cs`: `KeyRange Compile(ConditionNode, KeySchema)`: exactly one partition equality and at most one sort key clause of the allowed forms, else `ValidationException` with DynamoDB's `Query key condition not supported` / `KeyConditionExpressions must only contain one condition per key`.
- `Projection.cs`: `Item Apply(Item)` for a parsed projection (overlapping paths rejected as DynamoDB does).
- Entry point `Expressions.cs` (the seam P3/P4 code against): `ParsedCondition ParseCondition(string, PlaceholderScope)`, `ParsedUpdate ParseUpdate(...)`, `KeyRange ParseKeyCondition(string, PlaceholderScope, KeySchema)`, `ParsedProjection ParseProjection(string, PlaceholderScope)`.

**Storage** (`Fake/Storage/`)
- `FakeDatabase.cs`: `Lock Gate`, `TimeProvider Clock`, `SortedDictionary<string, FakeTable> Tables` (ordinal, which is also `ListTables` order), `IdempotencyCache` (token -> request hash + answer + time), `FakeTable GetTable(name)` (throws `ResourceNotFound`), `Create`, `Delete`.
- `KeySchema.cs`: `(string PartitionKeyName, ScalarAttributeType PartitionKeyType, string? SortKeyName, ScalarAttributeType? SortKeyType)`; `ItemKey KeyOf(Item)`, `ItemKey ReadKey(Item keyMap)` validating names, types, emptiness and sizes; `bool Covers(Item)` (sparse index test).

- `FakeTable.cs`: name, ARN (`arn:aws:dynamodb:us-east-1:123456789012:table/<name>`, the account and region `StubResponse` uses), `KeySchema`, attribute definitions, billing/throughput, `TableClass`, TTL (`attribute`, `TimeToLiveStatus`), `CreationDateTime`, `IReadOnlyList<FakeIndex> GlobalIndexes`, `LocalIndexes`, stream spec (P6). `Item? ### What is reused from DynaSharp, and why that keeps the fake an oracle
Reused: `AttributeValue`, `Item`, `AttributeValueConverter` (item JSON codec, read and write; it is checked against `real_aws_responses.json` recorded by the Parity Suite, and the fake's own unit tests use hand-written bodies, and the Parity run uses the JS SDK, so a symmetric codec bug cannot hide), `DynamoDbReader`/`DynamoDbWriter` as the codec's carriers, `WireNames` (enum spellings, one source of truth that `WireNamesTests` checks against botocore), `ErrorMapper.Map` (only to turn a `FakeError` into the DynaSharp exception for the direct API), `StubHandler`/`StubResponse`/`RecordedRequest`/`StubClient` (the handler seam), `TableSchema`/`TableAdministration` for `CreateTable<T>` (the same code `Table<T>.CreateTable()` runs, so a table from an entity is what the entity's command would create), the public `Requests.CreateTableRequest`/`TableDescription` records for the direct API (the wire path parses JSON itself and converts to the same internal `FakeTable`; the direct API builds `FakeTable` from the record; one `FakeTable` either way).
Must stay independent: expression tokenizer/parser/evaluator (the generator's parser cannot be referenced and checks only; `ExpressionWriter` and `RecordedRequest`'s text renderer are the client's view and would make the fake confirm the client), request parsing (`Requests/*` records have writers only; parsing into them would mean writing readers in `DynaSharp` for the fake alone), response writing (`Operations/*ReadResponse` are the readers the fake must satisfy, not reuse), numbers (`DecimalNumber`, not `DynamoDbNumber`), ordering (`AttributeComparer`, not `KeyText`/`KeyWriter`), size accounting, capacity arithmetic, table description JSON (written by the fake, read by `TableJson`).

### Risks and the part most likely underestimated
1. **The expression engine's semantics, not its grammar.** Parsing is a known shape (the generator's parser is a reference for the grammar). The time goes into DynamoDB's type rules per operator and function, the update path rules (overlaps, missing parents, list indices, set arithmetic, `DELETE` emptying a set, `ADD` creating attributes, upsert writing keys), 38-digit arithmetic and canonical number output, `UPDATED_OLD`/`UPDATED_NEW` deltas for nested paths, and the error messages of each. Budget P2 as a full week and expect it to be the one that slips; the vectors from DynamoDB Local are the way to find the cases before the Parity run does.
2. **100 % branch coverage and Stryker over 6 to 8 k lines of fake.** The gate includes `DynaSharp.Testing`. Every error branch of every reader needs a test; a package that lands code without its tests blocks everybody. Tests are part of each package's size above.
3. **Capacity and size arithmetic** against exact assertions in `ConsumedCapacityTests` and the 1 MB page: one `ItemSize`, used everywhere, with the documented rules; the fake must match what the tests state DynamoDB does, not what an emulator happens to report (`Gap.TransactionCapacityPerItem` shows the emulators disagree with each other already).
4. **Seam drift between P3 and P4** on `Capacity.cs` (both halves) and on condition handling in P1's `PutItem`/`DeleteItem`: assign the files as above and keep `Capacity` split into `ReadCapacity.cs` (P3) and `WriteCapacity.cs` (P4) if the two implementers prefer no shared file.
5. **The HTTP tool.** `HttpListener` on Windows needs a URL ACL for a non-admin user on `127.0.0.1:<port>` (to verify at implementation; `netsh http add urlacl` once, or run the Parity script on Linux/CI, which is where `parity.yml` runs). The JS SDK v3 may or may not validate `x-amz-crc32`; emitting it costs nothing. The suite's SigV4 is never verified; the fake's region/account in ARNs is fixed to us-east-1/123456789012 like `StubResponse`.
6. **Scope creep toward fine print.** The temptation is to make tier 3 pass. The decision row of 2026-10-31 says no: fine print stays with emulator-backed tests. Section 2's "Out" list and the "a fake gap may only name what Out names" rule are the fence.
7. **Operation registry completeness.** Every `X-Amz-Target` the client can send (`Operations/*Operation.cs` `Name` constants, 21 today including streams) must be either a handler or an explicit `UnknownOperation` entry; a unit test enumerates the `IOperation` names from the unit test project (which may use reflection) against the registry, so a new operation in `DynaSharp` fails the fake's test until someone decides.

## Addendum: docs rule (from the user, applies to every package)

Every package documents the fake as v1 docs. `src/DynaSharp.Testing/README.md`, `docs/testing.md` and the XML docs of `FakeDynamoDb` describe what the fake does: the operations it answers, the semantics a test can rely on, the "Out" list of section 2 stated as what the fake is not (eventual consistency, throttling, PartiQL, ...) and how it answers an unknown operation or an unsupported member. No disclaimers, no status notes, no "not yet", "planned", "coming with P6", "has not run against the Parity Suite" and no scores. Open work, the package status, the Parity score table, the fake's `Gaps` rows and every decision go to `spec/tasks.md` under M4; `spec/api.md` and `spec/architecture.md` describe the surface and the code as they stand at each merge, and nothing beyond it. Concretely:
- P1 writes the README section and the `docs/testing.md` section for what P1 ships; P2, P3, P4 and P6 extend those same sections with their operations and semantics in the commit that lands them, never ahead of them.
- Streams before P6: the docs say nothing about streams on the fake; the "Out" list in docs/testing.md names streams as not part of the fake. P6 removes that line and adds the streams section in its own commit.
- The Parity Suite appears in `docs/testing.md` only as the conformance measure the fake is held to (one sentence), with the score and the run log in `spec/tasks.md`.
- A reviewer rejects any package whose docs contain "not yet", "planned", "TODO", "preview", "experimental" or a score.
